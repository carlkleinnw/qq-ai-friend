# 稳定性与日常可用性验收

日期：2026-10-21。交付版本：本项目 0.1.1；运行框架保持 AstrBot 4.29.1，原有两个陪伴/记忆插件保持固定版本。目标为本机个人使用，先完善大肥鱼，保留 GPT大人的配置、人格和文字模式。

## 实际交付

| 内容 | 实现与证据 |
| --- | --- |
| 启停与重复启动 | 复用已安装 filelock 串行处理启停；检查进程身份和任意端口占用；启动等待放宽至 120 秒。两个独立测试进程竞争启动入口时，处理顺序为开始/结束/开始/结束，未并行进入启动动作 |
| QQ 恢复 | 继续使用 QQ 官方 SDK 的重连队列和会话恢复；单元测试确认断开后进入原生重连队列。真实账号停用并恢复连接后，手机收到新的模型回复和语音 |
| 模型失败提示 | 大肥鱼使用独立模型配置，引用原来的密钥来源，网络操作超时 25 秒，原生最大尝试次数 2。临时本地不可连接提供商不使用真实密钥；手机实际收到简明中文错误提示。恢复后再次收到语音和文字，临时提供商已删除 |
| 消息防重 | 未找到 QQ 入站防重能力，新增小型原生事件钩子插件，使用 SQLite 唯一约束按完整会话与真实消息 ID 判断，保留一小时。并发、重新打开数据库、不同机器人和不同 ID 均有测试；真实 QQ 事件进入账本后，重放该事件被原生钩子停止，没有生成第二条模型回复 |
| 语音超时 | 复用 Edge TTS 和原有文字回退。修复适配器忽略配置超时的问题，仅给原有网络保存操作套用 asyncio 超时；模拟停滞请求按配置结束，保留原生 RuntimeError 契约，后续回复阶段回退文字 |
| 提醒失败与中断 | 在原有 CronJobManager 中保留并暂停明确失败的一次性任务；正常成功仍移除。取消不误记成功，重启不盲目重放上次中断的任务；启动时超过原生 300 秒宽限的逾期任务转为失败暂停。畸形旧任务不阻止其他任务恢复 |
| 备份覆盖 | 复用原生导入导出；补齐共享清单漏掉的 CronJob，防止提醒不在备份里。用隔离数据库实际导出/导入了带有会话归属、失败原因和暂停状态的提醒，核对任务 ID 和字段保持 |
| 真实数据恢复 | 停服后导出一致备份，逐个核对源目录与 ZIP 文件内容。用全新目录实际导入，再导出比较数据库记录和所有备份文件，并检查 SQLite 完整性。没有启动恢复副本的 QQ、没有覆盖当前聊天 |
| 日常入口 | 启动、停止、日常状态检查、备份、检查备份能否恢复，以及可选登录后启动。Windows 原生快捷方式在 E 盘隔离目录实际创建、读取和删除；未替用户启用真实登录启动 |
| 运行观察 | 在维护重启后，持续检查本机 API 与两个连接进程状态，结果见 runtime-observation.json。这是短时观察，不等于 24 小时在线证明或手机端持续投递证明 |

## 上游测试兼容问题的处理

之前的失败分成两类，未通过改写生产逻辑来迎合静态测试：

1. 唤醒测试夹具缺少 AstrBot 4.29.1 要求的 `db_helper`、`astrbot_config_id`。在测试副本补齐 `None` 数据库与测试配置 ID；生产框架本身支持无数据库的自动命名记录器。
2. 静态装饰器检查误将两个插件生命周期缓存失效钩子和两个只处理当前事件的唤醒文本钩子视为必须绑定人格存储。已逐个审查，并用完整 AST 摘要固定这四个函数；仅在复制的检查中排除这四个已审查入口，其他所有入口的断言保留。函数改变时检查脚本会拒绝沿用结论。

`scripts/check_upstream_compat.py` 在私有目录复制固定来源后运行，不修改原始 vendor、生产插件或原始测试。指定的四个回归文件合计 **103 项通过，3 个子测试通过**；明确传入真实记忆插件根目录，没有跳过先前缺失依赖的两项。不能将这句话解释为“所有上游项目的全部测试通过”。

本项目新增与既有测试覆盖平台重连、请求有限重试、并发防重、启动互斥、超时、失败提醒、备份安全和真实数据层回归。最终数量以 `verification/stability-checks.json` 和本轮 JUnit 结果为准。唯一已知运行警告为上游 audioop 的 Python 3.13 弃用提示；当前锁定 Python 3.12，未通过禁用警告掩盖。

## 复用与本地修改边界

没有新增对话引擎、调度引擎、语音模型、管理前端或备份格式。新增的是入口脚本、检查脚本和小型消息防重钩子；防重使用标准 SQLite 原子约束，后台线程避免阻塞事件循环。原始第三方检出保持干净。

已安装组件有以下可审阅、固定文件摘要保护的本地兼容修复：

- `repair_memory_panel.py`：上一阶段的传统面板枚举修复。
- `repair_tts_timeout.py`：Edge TTS 网络超时。
- `repair_cron_failure.py`：一次性任务失败、中断、逾期记录保留与暂停。
- `repair_backup_coverage.py`：导入和导出共用的提醒表映射。

这些修复的原文件仅备份到 runtime/backups；升级版本或文件有其他修改时拒绝覆盖。重建环境时先应用对应修复再启动；在新环境恢复本项目备份前尤其要先补齐提醒表映射。

## 明确的使用边界

- QQ 无网络时无法发送断网通知，也不承诺补收所有离线消息。模型请求有重试和网络超时，整轮仍可能包含多次模型或工具操作，不能当作固定总时限。
- 消息防重覆盖一小时内有消息 ID 的重复投递。缺少 ID 的事件放行，不按文本误判；崩溃可能发生在领取事件之后，因而不是“恰好一次”保证。无回复时应以新消息重发，并先核对有副作用的操作。
- 提醒投递状态不确定时不会自动补发。到未来任务确认失败记录、收件情况后手动重试或改期；循环提醒沿用原生下一周期策略。运行中睡眠造成超过宽限的漏触发仍需查看任务，重启时会处理逾期状态；没有把本机程序包装成离线也可投递的服务。
- 备份 ZIP 包含私人配置与可能的密钥，保留在本机。源码 ZIP 不含私人数据和运行环境；仅拥有源码 ZIP 无法恢复历史聊天。备份窗口不要直接关闭；若被取消，先检查运行状态再启动服务。
- 已只读核对本机当前电源方案，自动睡眠超时为 0；没有修改系统设置。手动休眠、合盖、关机、退出 Windows 仍会影响运行。登录后启动是用户自行选择的入口，未默认启用。
- 没有进行整机断网、真实关机、全天压测或云服务器部署；实际验证的是原生连接恢复机制、真实账号重新连接、隔离模型连接故障和恢复、数据恢复及短时运行状态。

日常说明在根目录《交付说明_稳定版.md》。人设预设和 QQ 简介联动按用户要求仍留在最后。
